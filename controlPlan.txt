Assignment: Comparative Analysis of Control Plane Overhead Across Kubernetes Schedulers
Objective
The objective of this experiment is to quantitatively evaluate the control plane resource overhead introduced by different Kubernetes schedulers under the same workload conditions.
Most research evaluates schedulers only based on application-level performance metrics such as latency, throughput, or scheduling time. However, schedulers themselves consume CPU and memory resources within the Kubernetes control plane. This experiment aims to compare these overheads and determine which scheduler is more lightweight and efficient.
The expected outcome is a comparative study of the resource consumption of the default Kubernetes scheduler and several custom schedulers while handling an identical workload.

Comparative Analysis
After completing all experiments, perform a detailed comparative analysis addressing the following questions:
1.	Which scheduler consumed the least CPU resources? 
2.	Which scheduler consumed the least memory? 
3.	Which scheduler imposed the highest load on the Kubernetes API Server? 
4.	Which scheduler generated the highest control-plane overhead? 
5.	Did any scheduler significantly increase etcd or Controller Manager resource utilization? 
6.	How did the scheduling latency vary across schedulers? 
7.	Is there a trade-off between scheduler complexity and control-plane resource consumption? 
8.	Based on the experimental results, which scheduler appears to be the most lightweight while maintaining effective scheduling performance?

Expected Outcome
The expected outcome of this assignment is a comprehensive comparison of the control-plane overhead introduced by different Kubernetes schedulers. The results should clearly identify:
•	The CPU and memory footprint of each scheduler. 
•	The impact of each scheduler on key control-plane components (Scheduler, API Server, Controller Manager, and etcd). 
•	Whether advanced scheduling strategies incur significant additional overhead compared to the default Kubernetes scheduler. 
•	A quantitative basis for assessing the efficiency of lightweight scheduler designs, which will directly support the motivation and evaluation of our proposed event-driven scheduler (NEXUS) in the research paper. 
Important Notes
•	Ensure that only one scheduler is active during each experiment. 
•	Use identical cluster configurations, workloads, and monitoring settings for every scheduler to maintain fairness. 
•	Record all observations systematically and preserve raw metric exports for future validation. 
•	If any scheduler exhibits unexpected behavior (e.g., scheduling failures, crashes, or excessive resource usage), document these observations along with relevant logs.
